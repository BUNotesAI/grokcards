### 用户关键决策(sub-stage 1 review 时四轮澄清的结果)

- **Task 预留**:Task 虽然是现有的渲染节点(`EntityKind` 含 "task"),但 Phase B1 暂不接入菜单 —— `NodeKind` union 不含 "task",类型层不埋技术债,后续独立 task 接入时只需扩 union + 几处 applies_to
- **Phase B 拆成 B1/B2**:B1 纯 TS(复用现有 Rust command),B2 扩 Card/Question/Task 的 color schema(Rust 变更)。Phase B1 结束时把 B2 放到 Next,不让纯 TS 重构和 schema 变更混在一个 PR
- **Alias 不含 edit_title**:Alias 没有独立 title,视觉上借 source card 的 title 渲染,edit 对 alias 没有语义
- **Card 不含 delete**:Card 生命周期由 CLI/agent 管理,UI 菜单暴露 delete 风险高,保持现状
- **copy_title 统一为 copy_uuid_title**:砍掉 Card 专属的 `onCopyTitle`,所有节点都是 `UUID:{id} {normalize(title)}`;normalize 方向不重复(`normalizeCardTitleForClipboard` 剥离 md vs `normalizeBoldMarkdown` 修正渲染,两者相反方向)
- **canonical order 全局统一**:所有节点菜单项按 catalog 里的 `order` 渲染,不允许 per-kind 顺序覆盖
- **Delete 标签统一**:原 "Delete alias" / "Delete section" 改为 "Delete"

### 防火墙落地

- **NodeKind union 限定**:`"card" | "alias" | "note" | "question" | "section"`,Task 不在其中 → 传 `{kind: "task"}` 给 `NodeMenuConfig` 编译失败
- **Capability variant 写死 ui_kind**:`SetColorCapability.ui_kind = "custom"` 是类型字面量,const 初始化传 `ui_kind: "plain"` 会编译失败
- **visibility 规则写入类型**:`MoveToSectionCapability.visible = "sections_not_empty"` 必须存在 / `RemoveFromGroupCapability.visible = "in_section"` 必须存在
- **destructive 写入类型**:`DeleteCapability.destructive = true` 必须存在
- **NodeCapabilityHandlerMap 单一声明源**:per-NodeKind handlers 用 `Pick<NodeCapabilityHandlerMap, ...>` 裁剪,drift 风险集中在此一处
- **渲染 dispatch 的 cast 是 sound 的**:`menu.handlers as Partial<NodeCapabilityHandlerMap>` —— 每个 Pick 子集都是 HandlerMap 的 Partial,结构子类型合法

### 真实 UX 变化

| 变化 | 影响 |
|---|---|
| Card 菜单 `Copy title` → `Copy UUID + title`(带 UUID) | 用户粘贴 Card 标题时会多出 `UUID:card_xxx ` 前缀,是用户明确要的 —— 配合 agent + CLI 定位 |
| Alias 菜单**新增** `Copy UUID + title` | 之前没有复制入口,现在 alias 可 copy `UUID:alias_xxx {source card title}` |
| Section 菜单**新增** `Copy UUID + title` | 之前 Section 菜单只有 Delete,现在多了 copy |

所有其他菜单项(draw_connection / related / create_alias / jump_to_source_card / edit_title / move_to_section / remove_from_group / delete / set_color(Note))**行为与旧版本完全一致**,只是组织方式从 5 份 hardcoded 变成 catalog 驱动。

### 踩的坑

无明显踩坑。一个小注意点:

- **`data.sections` 之前不在 menuHandlers useMemo 的 deps**:原代码的 copy 函数都按 kind 各查一个 data field(cards/notes/questions),不需要 sections。合并成 `onCopyEntityUuidTitle` 后,Section 的 title 要从 `data.sections` 查,deps 漏掉会导致 stale closure(section 改名后 copy 出来是旧 title)。补上 `data.sections` 到 deps。

### 建模 DRY 优化(sub-stage 3 中途的重要 refactor)

sub-stage 2 的初版 type sketch 把 per-NodeKind handlers 写成 5 个独立 interface,每个声明
`copy_uuid_title: () => void; draw_connection: () => void; ...`。sub-stage 3 写 NodeContextMenu
渲染时发现:单一渲染路径需要从 `menu.handlers` 按 `cap.kind` 动态取 handler,没有通用类型
表达"menu.handlers[cap.kind]"的签名。

refactor:引入 `NodeCapabilityHandlerMap` 作为单一声明源,per-NodeKind handlers 改为
`Pick<NodeCapabilityHandlerMap, ...>`。好处:
- 字段签名单一源头,少一份维护
- `menu.handlers as Partial<NodeCapabilityHandlerMap>` 是 sound cast(结构子类型)
- 渲染时 `handlerMap[cap.kind]` 正确推出签名(Partial 的 indexed access)

这个 refactor 同时落在 sub-stage 3 的 `29d1fb8` commit 里。
