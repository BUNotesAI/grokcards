### Finding 1 的关键技术决策

Handoff 原 plan 说"SQL mapper 通过 serde lowercase rename 无缝 deserialize,无需改 SQL",但 **rusqlite 用自己的 `FromSql` trait 而不是 serde**,`r.get::<_, TaskStatus>(col)` 需要显式 impl。解决方案:

1. **`impl FromSql for TaskStatus`** —— 内部 delegate 到现有 `parse_task_status(&str)`,非法字符串装进 `FromSqlError::Other(Box<KeysightError>)`
2. **`impl ToSql for TaskStatus`** —— 内部 delegate 到 `task_status_to_str`,返回 `ToSqlOutput::Borrowed(ValueRef::Text(...))` (Copy 类型零分配)
3. **`extract_keysight_err(e: rusqlite::Error) -> KeysightError`** helper —— 对 `FromSqlConversionFailure` 做 downcast,还原装进 box 的 `InvalidTaskStatus`,回到 KeysightError enum 变体

**P1-3 回归测试 `test_update_task_rejects_invalid_legacy_status` 保持绿色** —— legacy "wip" 脏数据从 `get()` 读取路径直接 loud fail(而非原来在 `update()` 内部 parse 失败),语义等价 + 防御更早。

`domain/task::update` 原来的 `let current_status = parse_task_status(&current.status)?;` 调用点消失 —— `current.status` 已是 TaskStatus(Copy),直接 `input.status.unwrap_or(current.status)`。

### 关键技术决策回顾

**1. line_index 不跨 IPC** —— codex review 1 指出把 parser 位置信息暴露成前后端共享模型会让写契约天然 stale。V2 定稿 `Subtask { text, done }` 单一 IPC 类型,`ParsedItem { subtask, line_index }` 是 Rust 内部私有类型,write path 用 `parse_task_checklist_with_positions` 在本地拿到位置信息做替换,TS 永远看不到 line_index。

**2. 单 block only + typed error fail-closed** —— V1 设想的 "全删 + 首位插回" 算法会把原本夹在 checklist 行之间的自由文本挪位置,codex review 1 发现这个 bug。V2 改为"只支持单连续 block,多 block 时 Rust 写路径返 typed error"。读路径宽松(progress 徽章仍显示所有 item),写路径严格(保持文档结构不破坏)。

**3. AppError typed error 通路(Phase 6.0)** —— CC 在 review response 1 里假设 TS 可按 `err.kind === "MultiBlockChecklist"` 穷尽 match,但 codex review 2 发现当前代码库 `AppError` 只有 `Todo(String) / Keysight(String)` tuple variants,`impl From<KeysightError> for AppError` 做 `to_string()` flatten,TS 侧收到的是 `{ kind: "Keysight", message: "..." }`,没法结构化 catch 细粒度错误。V2 的 Phase 6.0 refactor:AppError 改成 struct variants(`Todo { message }` / `Keysight { message }`),serde 从 `tag + content` 改为仅 `tag`,新增 `MultiBlockChecklist { task_id, block_count }` 带 `#[serde(rename_all = "camelCase")]` 生成 TS 侧 `{ kind, taskId, blockCount }`。从此所有跨 IPC 的 structured error 都可以加新 variant 走同样路径。

**4. V1.1 modal 无 content textarea** —— codex review 1 §A+§B 指出如果 modal 同时编辑自由文本和 checklist,就会引入"content 和 subtasks 两个状态如何合并"的同步问题,本质上是在 modal 里塞一个半结构化 markdown 编辑器,复杂度不匹配 V1.1 scope。V2 接受 scope 收敛:modal 只做 title/status/area/color + ChecklistEditor,`task_update_with_subtasks` 无 content 参数,Rust 从 `current.content` 继承非 checklist 自由文本作 merge base。自然消解所有同步问题,自由文本 body 编辑延 V1.2。

**5. PointerSensor activationConstraint** —— codex review 1 §4 指出当前 `KanbanCard` 把 @dnd-kit listeners 铺满 root,双击区域和拖拽区域是同一 DOM。codex 原建议两选项(drag handle / isDragging check)都有代价。CC 换成第三条路:`activationConstraint: { distance: 8 }` —— @dnd-kit 官方推荐,一次配置覆盖整个 DndContext,drag 只在 pointer 移动 > 8px 后激活,纯 click 永远不触发 drag,加 `drag 不触发 edit modal` 回归锚点测试。

**6. UX follow-up(Phase 6.6 之后)** —— 用户 V1.1 首次 walkthrough 反馈两点:(a) 双击打开 modal 不够直接,改单击更自然;(b) color 字段让用户填 hex 字符串 `#xxx` 体验太糟,应该和 canvas 一样用 swatch picker。CC 的响应:
- 双击改单击由 `onDoubleClick` → `onClick` 一行改动完成。Click 和 drag 的互斥由现有 `activationConstraint: { distance: 8 }` 继续保证 —— 真实浏览器行为是 pointer down/move/up 若检测到移动发生则不 fire click 事件,天然互斥。jsdom 测试环境也一样
- color 从 `<input type=text>` 改成 swatch row,直接 import keysight `NodeContextMenu` 的 `NOTE_COLORS`(7 色)+ 加一个 ⌀ clear 按钮。每个 swatch 是圆形按钮带 aria-pressed 状态高亮,视觉和 canvas NoteColorRow 完全一致。跨 feature 的 color preset 复用保证了 task 在 Kanban 和 canvas 上看到的颜色一致
- 这次 follow-up 是 Phase 6.6 的 UX polish(codex review 没涵盖),commit `e9d3ff4` 单独提交,+3 新测试覆盖 swatch 预填/切换/clear
